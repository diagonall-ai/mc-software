# Data Model Guide

This file defines the database rules for this repository.

Read this before adding tables, relations, indexes, repositories, or migrations.

## Core Rule

Optimize for explicit ownership, bounded reads, prepared statements, and migrations that can be inspected before they are applied.

## Current Baseline

The starter uses Cloudflare D1 with Drizzle:

- schema: `app/db/schema.ts`
- Better Auth schema: `app/db/auth.schema.ts`
- repositories/services: `app/db/*.ts`
- migrations: `drizzle/migrations/`
- config: `drizzle.config.ts`
- runtime binding: `env.DB`

Better Auth tables include user, session, account, verification, organization, member, invitation, API key, OAuth application/token/consent, and MCP requirements.

## Runtime Database Access

- Use `drizzle(env.DB)` from `drizzle-orm/d1`.
- Keep database imports server-only.
- Do not import `app/db/client.ts` from client components.
- Do not add HTTP database URLs.
- Do not call Cloudflare REST APIs from app runtime to query D1.
- Do not concatenate user input into SQL.

## Table Design Rules

When adding a table:

- define it in `app/db/schema.ts` or a schema file exported by it
- give it one clear responsibility
- use string IDs generated by app code
- store foreign keys explicitly
- add indexes for lookup and ownership paths
- avoid unbounded embedded JSON arrays when a child table is the real shape

## Ownership Rules

Ownership must be enforceable in server-side repositories/services, not inferred only in the UI.

Rules:

- derive the current user from Better Auth server-side
- derive active organization from the session or the membership table
- use `app/lib/orpc/authorization.ts` helpers before tenant-scoped reads or writes
- check organization ownership before reads, writes, deletes, and exports
- reject unauthorized writes with an error

Do not:

- accept a `userId` or `organizationId` from the client and trust it
- rely on route guards alone for data protection
- return fake empty data for authorization or database failures

## Query Defaults

Default to bounded reads.

- Paginate user-facing lists.
- Use indexed predicates for ownership and common filters.
- Use dashboard summaries only over bounded datasets or with intentional aggregate tables.
- Avoid N+1 queries when a join, `inArray`, or batch fetch works.

## Mutations

Mutations should do one write job well.

- Validate input before writing.
- Write only the fields intended to change.
- Keep related writes in one repository/service when they must stay consistent.
- If external I/O is needed, split it from the database mutation.

## Files And Blobs

This template intentionally has no blob storage. Do not rebuild file uploads on D1.

If a real feature needs files later:

- use R2 for blobs
- store metadata in D1
- enforce ownership before reads and deletes

## Realtime

Realtime subscriptions are out of scope for the template. Use SSR loaders and explicit revalidation by default.

If a real feature needs realtime later, choose the Cloudflare primitive deliberately and document the boundary first.

## Verification After Schema Changes

After changing schema or repositories:

```bash
pnpm drizzle-kit generate
pnpm lint
pnpm typecheck
pnpm build
pnpm wrangler deploy --dry-run --config dist/server/wrangler.json
```

Inspect generated SQL before applying:

```bash
pnpm wrangler d1 migrations apply DB --local --config wrangler.jsonc
pnpm wrangler d1 migrations apply DB --remote --config wrangler.jsonc
```
